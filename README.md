# 卒研前のアプリ開発練習計画

## 目的

卒業研究のテーマを決める前に、Flutterで小さなアプリを作りながら、企画・実装・動作確認・改善の流れを身につける。練習で得た経験を、卒研で必要になりそうなセンサー利用やデータ分析の検討につなげる。

この段階では、完成度の高い大規模アプリや卒研テーマの確定を目指さない。まず動くものを作り、分からなかったことや次に試したいことを記録する。

## 使用環境・言語

- Flutter / Dart
- Visual Studio Codeを基本の開発環境とする
- Android StudioはAndroid SDKやエミュレーターなど、必要な機能の利用に使う
- 必要に応じてPythonでデータの集計や可視化を試す
- Firebaseは、クラウド保存が必要になった段階で導入を検討する

## 開発において

- プロジェクトや作業データは、容量に余裕のあるDドライブを基本に置く
- まず小さい機能単位で作り、動作を確かめてから次の機能に進む
- 各アプリで「目的」「できたこと」「困ったこと」「次に試すこと」を記録する
- 個人情報や位置情報など、扱いに注意が必要なデータは練習で安易に収集・共有しない

## 練習の進め方

### 1. Flutterの基本

- 画面、ボタン、入力欄、リストを使った小さなアプリを作る
- 画面遷移と状態の更新を試す
- 入力内容を端末内に保存し、アプリ再起動後に読み込む

### 2. スマホ機能の利用

- センサーなど、卒研で使う可能性のある機能を試す
- 取得できるデータと、取得が難しい条件を確認する
- 計測結果を画面に表示し、必要なら端末内に記録する

### 3. データの活用

- 記録したデータを表やグラフで見られるようにする
- Pythonで簡単な集計・可視化を試す
- 必要性が出たらFirebaseへの保存や読み込みを試す

## 最初の練習案：センサー記録アプリ

スマホの加速度センサーの値を画面に表示し、計測の開始・停止と簡単な記録を行うアプリを作る。最初はAI判定やFirebase連携を入れず、センサー値を取得して表示・保存するところまでを目標にする。

### 最初の完成条件

- 計測を開始・停止できる
- 加速度の値を画面で確認できる
- 計測結果を端末内に保存し、一覧で見られる
- 実際に使って分かった制約や改善案を記録する

### 発展候補

- 計測データをグラフ表示する
- 静止・歩行などの簡単な状態判定を試す
- 判定結果と実際の活動を比べ、精度を確認する
- 複数端末や複数人でデータを扱う必要があればFirebaseを試す
- ルールベースの判定と機械学習による判定を比較する

## 今後取り組みたいデータ分析

Android実機がない間は、公開データを使ってPythonで分析やモデル作成を進める。Web版とF12は表示や操作の確認に使い、F12の向き・位置の値を実際の加速度データとして扱わない。

### 1. 加速度から活動を判定する

- **知りたいこと**：加速度の時系列から静止・歩行などの活動を判定できるか
- **データ**：時刻、加速度X・Y・Z、活動ラベル。可能ならジャイロも使う
- **機能案**：計測データをグラフ表示し、活動ごとの判定結果を表示する
- **モデル案**：まずルール判定を基準にし、特徴量を使う決定木やランダムフォレストと比較する
- **実機なしでの練習**：[UCI HARデータセット](https://archive.ics.uci.edu/dataset/240/human%2Bactivity%2Brecognition)を候補にする。歩行・階段昇降・座る・立つ・横になるなどのラベルがある。走行のラベルは含まれないため、走行も対象にする場合は別データを探す

### 2. 加速度から歩数・歩行テンポを推定する

- **知りたいこと**：加速度の周期的な変化から歩数や1分あたりの歩数を推定できるか
- **データ**：時刻、加速度X・Y・Z、歩行区間、正解歩数または正解テンポ
- **機能案**：推定歩数と歩行テンポを表示する
- **モデル・方法案**：最初は加速度の大きさと山の数を使うルール方式を試し、その後に歩行区間の分類モデルと組み合わせる
- **注意点**：活動ラベルだけの公開データでは、正解歩数との誤差を評価できない。正解歩数付きデータを探すか、実機を使える段階で照合する

### 3. GPS・速度・加速度から移動手段を推定する

- **知りたいこと**：徒歩・自転車・車・バスなどをセンサーデータから判定できるか
- **データ**：時刻、GPS座標、速度、加速度、移動手段ラベル
- **機能案**：移動中の手段を推定し、経路と一緒に記録する
- **モデル案**：まず速度や速度変化などGPS由来の特徴から分類し、加速度があるデータではセンサーを組み合わせて比較する
- **実機なしでの練習**：GPSと移動手段ラベルには[Microsoft GeoLife](https://www.microsoft.com/en-us/research/publication/gps-trajectories-with-transportation-mode-labels/)を候補にする。ただしGeoLifeはGPS軌跡が中心で、加速度を含まない。GPSとスマホセンサーを合わせて試す段階では、加速度・GPS・移動ラベルを含む[SHLデータセット](https://www.sussex.ac.uk/strc/research/wearable/locomotion-transportation)を候補にする
- **注意点**：位置情報は個人の行動が分かるデータなので、公開・保存範囲に注意する

### 4. 活動の時刻・継続時間を集計する

- **知りたいこと**：どの活動がいつ、どれくらい行われたか
- **データ**：時刻、活動ラベル、判定結果、計測セッション
- **機能案**：日ごとの活動時間、活動のタイムライン、歩数の推移を表示する
- **モデル案**：この部分は必ずしもAIを使わず、活動判定結果を時間ごとに集計する。将来は普段の活動パターンとの違いを検出する方法も試す
- **実機なしでの練習**：ラベル付き公開データやサンプル記録を時系列に並べて画面と集計を作る。実生活での活動傾向とは区別する

### 進める順番

1. UCI HARなどの公開加速度データをPythonで読み込み、活動分類の基準モデルを作る
2. 加速度グラフと歩数・テンポ推定を試す。正解歩数データがない間は、推定値の画面表示と信号の挙動確認までを行う
3. GeoLifeでGPS由来の移動手段分類を試し、必要に応じてSHLで加速度との組み合わせを試す
4. 活動ラベルと時刻を集計し、Flutter Webで日ごとの履歴を表示する

## データ収集・評価の共通ルール

- 生データには時刻、センサー値、正解ラベル、計測セッションを含める
- 活動分類では、学習データと評価データが同じ計測区間の重複にならないように分ける
- 正解ラベルがない数値は、モデル精度の根拠として扱わない
- 公開データで作ったモデルは、スマホ機種や持ち方が違う実機で同じ精度になるとは限らない。実機が使える段階で別途確認する

## 現時点での方針

センサーを使った活動記録は、卒研につながる可能性のある練習題材として扱う。卒研の研究目的や対象者、評価方法はまだ決めず、アプリを作って得た経験をもとに改めて検討する。

## 試験中の活動判定モデル

- 静止・歩行・走行を、1秒窓の加速度特徴量からRandom Forestで判定する
- 特徴量は3軸加速度の大きさから計算した標準偏差、範囲、隣り合う値の平均絶対変化量
- センサー値を受け取りながら0.25秒ごとに直近1秒を判定する
- 学習データは `stop_01/02.csv`、`walking_01/02.csv`、`running_01/02.csv`、`random_05.csv`。`random_06.csv` は学習に使わない評価用
- Notebookと同じ条件での `random_06.csv` 評価は22窓中21窓正解（95.5%）。データ数が少なく、同じ人・端末での記録なので試験的な結果として扱う
- JSONモデルの再生成には `tools/export_activity_model.py` を使う。CSVは `../activity_analysis` に置く
- 画面のモデル投票割合は確率校正済みの信頼度ではない
